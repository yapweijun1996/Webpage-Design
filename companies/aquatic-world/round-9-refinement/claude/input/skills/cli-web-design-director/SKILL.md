# CLI Web Design Director

Own the brief and acceptance decision. A worker's successful build, screenshot fidelity or self-score is evidence about that check, not proof of a satisfactory website. Skills improve instructions and review; they do not train model weights or guarantee taste.

## Establish the product contract

Read current user intent, relevant source and existing site before prompting a builder. Identify the audience, main visitor task, site type, required destinations, supplied facts/assets and expected finish. Distinguish a conversion landing page, a company website and an application. A reference homepage supplies visual evidence; it does not silently determine the whole product's architecture.

If ambiguity changes the experience, ask one focused product question while continuing independent research. Resolve technical choices from evidence. Do not require approval of routine design artifacts when implementation is already authorized.

Record a compact route/content/action table and a primary journey. For a requested multi-page site, specify independent URLs, meaningful page-specific content, direct loading, refresh and Back/Forward. Map global navigation to pages; use section anchors only for intentional in-page navigation. Empty wrappers around homepage excerpts do not satisfy this contract. For an explicitly requested one-page landing page, preserve that scope.

## Direct the design

Read [design-review.md](references/design-review.md) for redesign or subjective requests such as "impressive", "premium" or "professional". Translate them into observable hierarchy, typography, imagery, rhythm, interaction states and domain relevance. Separate functional gates from visual judgment.

Explain which qualities of a reference should survive and which may change to meet current scope. Inspect desktop and mobile crops before locking layout. Prefer a few deliberate visual decisions over generic decoration. Record content gaps as assumptions; do not manufacture business history, guarantees or inventory to fill pages.

For substantial work, create a self-contained brief and relevant design artifacts before execution. Ask a worker to document its page plan before coding, then continue implementation in the same run when authorized. Use a separate review checkpoint only when a real unresolved product choice warrants it. A design-only task ends at the requested design package.

## Prompt and operate the chosen CLI

Use [prompt-patterns.md](references/prompt-patterns.md) to compose a brief, implementation prompt or specific revision. Read [cli-operation.md](references/cli-operation.md) before launching a native CLI or arranging a comparison.

Preserve the selected provider and exact model. Check local help and actually available tools instead of assuming flags or browser access. Supply relevant sources and name their authority. Do not substitute a model, change global permissions, add reviewers or create extra paid runs merely because the skill was invoked. Current user authorization governs execution.

For paired comparisons, provide the same task, design direction, asset bytes, product acceptance and shared skill snapshot to both workers. Keep independent writable folders and immutable past deliveries. Record tooling/permission/effort differences; equal prompts alone do not isolate model ability. Neither worker may inspect the other's implementation.

## Accept the delivered experience

Review real rendered pages and perform the primary visitor journey independently of the worker's claims. Check each required route, global navigation from an inner page, current-page indicator, direct URLs, refresh, browser history, mobile menu, keyboard access and honest primary-action feedback. Test responsive composition on agreed viewports, including a narrow phone and intermediate width. Use available browser tools; record unavailable checks as not run.

Inspect the header and key layouts at full viewport size, not only tiny side-by-side thumbnails. For visual defects, state the viewport, observed problem, cause supported by source or computed layout, intended treatment and affected checks. Revise and re-check affected behavior rather than repeatedly issuing "make it better".

Report functional verification, visual judgment and user acceptance separately. User rejection keeps design acceptance open even if automated checks pass. Preserve historical scores with their original scope and limitations. Capture stable lessons with evidence and applicability; keep one-off company facts in the company folder.
